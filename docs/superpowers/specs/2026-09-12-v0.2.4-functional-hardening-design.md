# Censorship v0.2.4 Functional Hardening Design

**Date:** 2026-09-12
**Status:** Approved under the task's standing unattended-execution authorization
**Target:** `v0.2.4`

## Goal

Close four confirmed request-handling and release-packaging defects without changing CLIProxyAPI core, native ABI v1, configuration semantics, phase ordering, or generated artifacts by hand:

1. Gemini model text carrying thought-signature metadata currently bypasses every rule phase.
2. A full `strip` of a Claude scalar user message is forwarded as an invalid empty message and fails at the provider instead of locally.
3. Documented OpenAI Chat Completions and Responses text inputs outside message bodies bypass censorship.
4. Release outputs overwrite unrelated files that share the destination inode through a hard link.

The implementation must remain explicit, type-aware, role-aware, byte-preserving outside selected JSON string tokens, and compatible with `github.com/router-for-me/CLIProxyAPI/v7 v7.2.152`.

## Non-goals

- Do not modify CLIProxyAPI core or the module cache.
- Do not change native ABI ownership, pointer, length, or `C.GoBytes` behavior.
- Do not add a generic recursive string walker.
- Do not inspect tool-call arguments, names, IDs, code, commands, environment values, encrypted state, grammar definitions, URLs, paths, binary data, JSON property names, enum values, or arbitrary strings in schemas.
- Do not mutate Gemini thought signatures, Claude thinking/signature blocks, or OpenAI reasoning/encrypted items.
- Do not infer undocumented replay visibility for entire provider response objects.
- Do not hand-edit `.integration/` or `dist/`.
- Do not change `words`, legacy YAML, scope enums, matching semantics, or the fixed `block` -> `strip` -> `obfs` order.

## 1. Gemini signature-bound visible text

### Confirmed defect

A native Gemini `Part` can contain ordinary visible `text` together with `thoughtSignature`. The signature is metadata preserving prior model reasoning; it is not a discriminator that turns visible text into a machine-only part. The current shared part scanner rejects the whole part when any supported signature carrier is non-null, so a later request can carry a blocked term to the model without inspection.

Google documents that final text parts may contain signatures and recommends returning them for text/chat quality. Function-calling current-turn signatures and image-generation/editing signatures have stricter replay requirements. Google requires signatures to be returned exactly as received inside their original `Part`; it does not document that arbitrary mutation of the signature-bound text is replay-safe.

### Selection contract

For `sourceFormat: gemini`, select `Part.text` when all of the following hold:

- the part is an object;
- `thought` is not JSON `true`;
- no non-null function, function-response, media, file, executable-code, or code-result discriminator is present;
- `text` is a non-empty JSON string.

The presence of any non-null supported signature carrier does not suppress visible text selection:

- `thoughtSignature`;
- `thought_signature`;
- `extra_content.google.thought_signature`.

A JSON `null` signature remains equivalent to an unset signature. A signed part that also has a real machine discriminator remains excluded. Interactions selectors keep their current stricter typed-part behavior.

### Mutation contract

A selected span with a non-null signature carrier is signature-bound and immutable:

- `block`: inspect it normally and return the existing `censorship_blocked` response on a match. No provider request is sent.
- `strip` or `obfs`: if a rewrite rule matches the signature-bound span, terminate locally with HTTP 400 and `censorship_invalid_request`. Use the message `censorship cannot rewrite signature-bound text`.
- no matching rewrite rule: preserve the complete request byte-for-byte.

Never remove, decode, normalize, regenerate, or alter a signature. This avoids both silent bypass and provider-invalid or quality-degrading replay.

## 2. Claude scalar user-message validity

### Confirmed defect

Anthropic defines scalar `messages[*].content` as shorthand for one `TextBlockParam`. A text block requires a non-empty `text`. The current selector marks array-form text blocks as non-empty but does not mark the equivalent scalar user content. Fully stripping a valid user scalar therefore forwards `content: ""`, and Anthropic rejects it upstream.

### Contract

Mark a non-empty scalar `messages[*].content` with `role: "user"` as requiring a non-empty post-rewrite value.

- A full `strip` terminates locally with HTTP 400, JSON content type, `censorship_invalid_request`, and the existing message `censorship rewrite would make a text field invalid`.
- A partial strip remains valid and preserves the rest of the request exactly.
- `block` and `obfs` behavior is unchanged.
- Do not delete the message or merge turns.
- Do not generalize this requirement to scalar assistant prefills, top-level scalar `system`, or scalar tool results without a provider contract proving those specific empty values invalid.

## 3. OpenAI documented model-visible text

### Confirmed defect

CLIProxyAPI invokes BeforeAuth with the raw entry-protocol body and `SourceFormat`, before provider translation. OpenAI explicitly sends tool definitions, schema descriptions, prompt-variable text, predicted output, and dynamically loaded tool definitions to the model. The current selectors inspect messages and selected result text but omit these documented input paths.

Selectors must operate on the documented entry-protocol contract. They must not guess the eventual compatibility backend or inspect fields merely because their names resemble text.

### Canonical scope mapping

- Conversation messages keep their existing canonical roles.
- Chat `prediction.content` uses `assistant`.
- Top-level Chat/Responses tool definitions and output-format descriptions use `developer`.
- Responses `prompt.variables` text uses `user`.
- `additional_tools` definitions use the item's documented role when it is exactly `system`, `developer`, `user`, `assistant`, or `tool`.
- `tool_search_output` and `mcp_list_tools` loaded definitions use `tool`.
- Responses local-shell skill descriptions use `user`, matching OpenAI's statement that skill metadata is added to user prompt context.
- `additional_tools` roles `unknown`, `critic`, `discriminator`, missing, malformed, or future values remain unselected.

### Chat Completions paths

Select these additional explicit paths:

1. `prediction.content` when it is a string.
2. `prediction.content[*].text` only for typed text parts.
3. Deprecated `functions[*].description`.
4. JSON Schema `description` annotations within `functions[*].parameters` and documented output schemas when present.
5. `tools[*].function.description` plus schema descriptions in its `parameters` and documented `output_schema`.
6. `tools[*].custom.description`; preserve custom grammar definitions.
7. `response_format.json_schema.description` and schema descriptions inside `response_format.json_schema.schema`.

### Responses paths

Select these additional explicit paths:

1. `prompt.variables.*` when the value is a string.
2. `prompt.variables.*` typed `input_text.text`, whether represented as one typed object or in an array of typed content objects.
3. `text.format.description` and schema descriptions inside `text.format.schema` for documented JSON-schema formats.
4. Supported descriptions in top-level `tools[*]` definitions.
5. Supported descriptions in `input[*]{type:"additional_tools"}.tools[*]`, using the item's role.
6. Supported descriptions in `input[*]{type:"tool_search_output"}.tools[*]`, using `tool`.
7. `input[*]{type:"mcp_list_tools"}.tools[*].description` and schema descriptions in each tool's `input_schema`, using `tool`.
8. `tools[*]{type:"shell"}.environment{type:"local"}.skills[*].description`, using `user`.

Supported tool-definition variants are explicit:

- `function`: `description`, plus schema descriptions in `parameters` and `output_schema`;
- `custom`: `description` only;
- `namespace`: `description`, then its documented nested tool definitions with the same owner role;
- `tool_search`: `description`, plus schema descriptions in `parameters`;
- `mcp`: `server_description`.

Other built-in tool variants remain unchanged.

### Schema-description traversal

A dedicated JSON-Schema annotation selector may recurse only through recognized schema-valued keywords. It selects a string `description` on a schema object, then descends through explicit schema children such as:

- map-valued `properties`, `patternProperties`, `$defs`, `definitions`, and `dependentSchemas`;
- schema-valued `items`, `additionalProperties`, `unevaluatedProperties`, `propertyNames`, `contains`, `not`, `if`, `then`, and `else`;
- array-valued `prefixItems`, `allOf`, `anyOf`, and `oneOf`.

It must not descend through `default`, `examples`, `enum`, `const`, arbitrary extension keys, property names, or ordinary request data. It must not select `title`, `$comment`, or any string other than the explicit `description` annotation.

### Required negative controls

Tests must prove that matching terms remain byte-identical in:

- function/custom/tool-search call `arguments` and custom-tool `input`;
- tool, function, namespace, and property names;
- JSON Schema property names, `required`, `enum`, `const`, `default`, `examples`, and unknown extension data;
- custom grammar `definition`;
- reasoning summaries/content and `encrypted_content`;
- program code/fingerprint, code-interpreter code, shell commands/environment, apply-patch diff/path;
- IDs, labels, namespaces, URLs, paths, status, annotations, logprobs, coordinates, key sequences, and file/image/audio data;
- local skill `name` and `path`, hosted skill IDs/versions, and inline skill bundle data;
- `ResponseOutputMessage.phase` and unsupported/future item types.

The new positive paths must exercise `block`, `strip`, and `obfs`, exact role gating, partial rewrite, and raw-byte preservation outside selected string tokens.

## 4. Release output hard-link safety

### Confirmed defect

`os.Create` and `os.WriteFile` open an existing destination inode for truncation. If an archive, per-archive checksum, or aggregate `checksums.txt` is hard-linked to an unrelated file, packaging exits successfully and overwrites the unrelated peer. Existing alias checks only compare paths known to the packager and cannot discover unknown peers.

### Write contract

All three output kinds must use one shared same-directory temporary-write and replacement path:

1. Keep current preflight alias, symlink, junction, and input checks.
2. Create an exclusive temporary file in the destination directory.
3. Write the complete archive or checksum content to the temporary file.
4. Close every writer and file, propagating close errors.
5. If the destination does not exist, rename the temporary file into place.
6. If the destination exists, move its directory entry to a unique same-directory backup, rename the temporary file into the destination, then remove the backup.
7. If installation fails after moving the destination, restore the backup to the original destination before returning the error.
8. Remove temporary files on every failure. Remove backups after success. If rollback itself fails, return both failures and retain the backup path for recovery instead of deleting the only surviving old destination.

The old destination inode is never opened for writing. Unknown hard-link peers therefore retain their original bytes. Normal replacement of a regular destination remains supported.

Use only the Go standard library. Keep `go run ./.github/scripts/package-release.go` valid; do not add a helper file that the current invocation would omit.

### Tests

Add cross-platform tests for unrelated sentinel hard links at each destination:

- direct archive;
- direct `.zip.sha256`;
- aggregate `checksums.txt`.

Each test must assert successful packaging, changed destination identity/content, and unchanged sentinel bytes. Existing output/input and known-output alias rejections remain intact.

Add deterministic failure-injection coverage for installation failure after destination staging:

- the old destination is restored byte-for-byte;
- the sentinel peer is unchanged;
- temporary files are removed;
- recoverable backups are removed;
- a rollback failure reports both errors and retains the recovery file.
